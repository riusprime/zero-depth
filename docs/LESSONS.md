# Lessons from Deathventory

Deathventory (`riusprime/deathventory`) is a turn-based backpack roguelike in Godot 4.7 by the same owner, built
with AI coding agents. In about 30 days (2026-09-07 → 2026-10-06) it went through:
- 26 released versions (v0.0.1 → v0.9.7);
- 429 commits in the visible history;
- about 65.8k lines of GDScript in `src/` across 294 files;
- 2,654 GUT test functions in 279 files.

This file turns what went wrong, and what went right, into rules for this game. Each row names where the rule is
enforced. **DV** means the Deathventory repo; its paths are given so a session with read access can check them.

## Process note: why there is one lead, not a task DAG

Deathventory's first phase (2026-09-07 → 09-08) ran a 54-task DAG (55 after a remediation task was added) with exclusive file leases, a coordinator and
many fresh worker sessions, mostly on non-Claude models. That phase produced the fabricated DV-920 and DV-930
evidence (L1). Later, leased work left the tooltip unwired because "`TooltipView` is outside the lease" (CX-30),
and a worker's 480-run sim matrix was thrown away because its base was 77 commits stale (CX-40).

From v0.2.0, Deathventory moved to a solo lead per version. v0.2.0's TASKS added a solo-lead mode and was built solo; from v0.3.0 the rule reads "the lead works solo". That is the model here: one
lead per version, with subagents only for read-only investigation and review
([`roadmap/ROADMAP.md`](roadmap/ROADMAP.md) §0.1). Deathventory never wrote down why it dropped the DAG; this
note records the costs that are documented.

## Lessons from Zero Depth

What went wrong in this game, what it cost, and the rule it became. The evidence is in the version's PROGRESS
History and evidence pages, linked per row.

| L22 | **Building before measuring.** v0.11.1's plan was built from a code audit's cost estimates, and the measurements overturned them several times: T1 put about 20 s a test on the boot, the hub walk and the arrival (under 2 s together); U3 called the content load the load-time problem (under 100 ms); V1 ranked moving enemies onto the crowd renderer first (their own `_process` was 3 µs each).
